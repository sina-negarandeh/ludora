# Aspect-Based Sentiment Analysis (ABSA)

**Status: Implemented (offline batch pipeline), on a sampled subset of reviews.**

## Problem

Star ratings don't say *why* someone liked or disliked a game. Extract per-aspect sentiment (e.g. "the rulebook was confusing" → `Rulebook: negative`) from free-text reviews, so the product can show "what players actually said about X," not just an average score.

## Inputs and outputs

Input: a review's raw comment text, paired against each of a fixed 22-aspect taxonomy. Output: per `(review, aspect)`, a sentiment label (positive/negative — neutral predictions are discarded), a confidence score, and an evidence sentence.

## Taxonomy (22 aspects)

Gameplay, Mechanics, Strategy, Theme, Immersion, Replayability, Components, Artwork, Production Quality, Rulebook, Setup, Teardown, Learning Curve, Complexity, Downtime, Player Interaction, Balance, Luck, Player Count, Solo Play, Game Length, Value.

## Two implementations exist — only one is current

Git history (`git log --follow`) shows two distinct approaches were built, in this order:

1. **`scripts/absa_extract.py`** (commit `1aea258`) — calls a local **Ollama** server (`qwen2.5:7b`, downgraded from an originally-intended `qwen3:7b` per an inline comment) with a hand-written JSON-extraction system prompt, asking the generative model to output `positive|negative|mixed|neutral` per aspect directly as JSON. Reads from the CSV-based pilot filter (`pilot_absa_filtered.csv`). Untouched since its introducing commit — superseded, not deleted.
2. **`scripts/absa_extract_hf.py`** (commit `0e41dad`, "Migrate ABSA to HuggingFace DeBERTa and add stratification scripts") — the current pipeline, described below.

No commit message states an explicit reason for the switch (commit bodies in this repo are single-line subjects only — see [docs/case-study.md](../case-study.md) for what the git history does and doesn't support as evidence). What's verifiable is the direction of the change: from a generative LLM prompted for JSON, to a discriminative zero-shot classifier purpose-built for sentence-pair classification — a defensible engineering choice (discriminative classifiers are typically faster and more consistent for a fixed label set than prompting a generative model per item), but the *reason* is inferred, not documented in-repo, so it is stated here as an inference, not a fact.

## Current approach: DeBERTa zero-shot classification

`scripts/absa_extract_hf.py` uses `yangheng/deberta-v3-large-absa-v1.1` via HuggingFace `transformers` (`AutoModelForSequenceClassification`, `mps`/`cuda`/`cpu` auto-detected). For each review, the **whole review text** is paired with each of the 22 aspect strings as a sentence-pair input (`tokenizer(text, aspect)`), batched 11 at a time. This is a 3-way classification per pair (negative/neutral/positive); only predictions with `winner_prob > 0.5` and a non-neutral winning label are persisted. Evidence is not generated by the model — it's a regex fallback that returns the first sentence in the review containing the literal aspect word.

### Quality filtering before extraction

`compute_quality_score()` (duplicated in `absa_filter.py` and `absa_extract_hf.py`) combines fastText (`lid.176.ftz`) language-ID confidence, review length, a keyword-match bonus, and a repeated-character spam penalty into a single score; reviews below `0.6` are excluded. Full formula in [docs/data/README.md](../data/README.md#data-quality-rules-as-implemented-not-as-a-policy-document).

### Coverage: sampled, not exhaustive

`scripts/generate_stratified_sample.py` builds a stratified sample cache (`data/stratified_samples.json`) covering the **top 100 ranked games**, up to **100 reviews per game** (proportionally allocated across positive/mixed/negative buckets, one best-quality review per unique user), for a **total of 10,000 reviews** — verified directly from the JSON file (100 keys, exactly 100 review IDs each). `absa_extract_hf.py --sampled` consumes this cache. There is no evidence in the repo of a full-corpus run across all ~4.2M reviews in `master_reviews.csv` — the production extraction, as implemented and invocable, covers the top 100 games only.

A separate, earlier pilot artifact, `data/processed/pilot_absa_filtered.csv` (13,332 rows, ~3.9 MB), belongs to the abandoned CSV/Ollama pathway (step 1 above), not the current DeBERTa pathway — it's evidence of an earlier iteration, not of current-pipeline coverage.

## Aggregation

`scripts/absa_aggregate.py` rolls `review_aspects` up into `game_aspect_aggregates` via a single `INSERT ... SELECT ... GROUP BY game_id, aspect ... ON CONFLICT DO UPDATE`: positive/negative/mixed/neutral counts, `total_mentions`, and `mean_sentiment` (average of `sentiment_score`).

## Serving

`AspectService` (`GET /api/games/{game_id}/aspects`) reads `game_aspect_aggregates` and returns it to `CommunityConsensus`, the aspect-cards UI component (`GameDetail.tsx`) — see [docs/product/features.md](../product/features.md).

## Downstream: LLM summarization ("Community Consensus" paragraph)

**Status: Implemented (offline script), single-game only.** `SummarizationService` (`backend/app/services/summarization_service.py`) turns ABSA aggregates into the paragraph shown above the aspect cards. It is called only by `scripts/generate_summaries.py` — **not by any live API route** — so this is a batch/offline feature, not something that runs on demand.

Pipeline, per game: require ≥15 `review_aspects` rows; select the top 5 aspects by `total_mentions` (minimum 5 mentions each); for each aspect, sample up to 100 evidence rows (proportional by sentiment) and ask the local LLM for a one-sentence mini-summary (`AspectMiniSummary` Pydantic schema); then a final LLM call combines all mini-summaries into a 2-3 sentence paragraph (`FinalGameSummary` schema), with an explicit anti-hallucination instruction in the prompt ("Do not invent information," "Every factual claim must be supported by one or more supplied themes"). Both calls use the OpenAI Python SDK against a local OpenAI-compatible server (`OPENAI_BASE_URL`, default `http://localhost:8080/v1`; `LLM_MODEL_NAME`, default `Qwen/Qwen3-30B-A3B-MLX-4bit`), with `response_format={"type": "json_object"}` and the target Pydantic schema embedded in the system prompt, validated on return via `model_validate_json()`.

`scripts/generate_summaries.py` hardcodes a single target game ("Brass: Birmingham") — there is no batch/loop-over-all-games invocation anywhere in the repo, so whatever `game_summaries` rows exist were generated one game at a time, by hand.

No evaluation of summary quality exists (no human rating, no faithfulness check beyond the prompt's own instructions).

## Evaluation

**None exists.** There is no ground-truth aspect annotation set anywhere in the repo, so no classification accuracy (precision/recall/F1 against a labeled set) can be computed or reported. The pilot artifact and the stratified-sample cache are coverage/sampling mechanisms, not evaluation datasets.

## Failure modes and limitations

- Coverage is limited to the top 100 ranked games and 10,000 reviews total — most of the catalog has no ABSA data.
- Neutral predictions are silently discarded, so aspects with genuinely mixed/neutral sentiment are underrepresented relative to clearly polarized ones.
- Evidence sentences are regex-matched, not model-selected, so they may not be the sentence that actually drove the sentiment classification.
- No accuracy evaluation exists — classification quality is unverified against any ground truth.
- Two ABSA implementations exist in the repo simultaneously (Ollama-based and DeBERTa-based); only the latter is wired into the current pipeline, but both are present and could be confused by a future contributor.
